# 付録B 導入チェックリスト

本書の各章から導かれる確認項目をまとめた。上から順に使うことを想定している。

印刷して使えるよう、チェックボックス形式にした。

---

## STEP 0：現状把握（第3章）

まず、いま何が動いているかを知る。多くの組織で、この一覧が存在しない。

- [ ] 部署内で自動的に動いているものを、すべて書き出した
- [ ] それぞれについて「いつ起動するか」を書いた（時刻／イベント／手動）
- [ ] それぞれについて「誰が設定したか」を書いた
- [ ] 設定者が不在・異動・退職しているものを特定した
- [ ] 誰も把握していないまま動いているものを特定した

> **危険信号**：一覧を作ってみて、初めて存在を知ったものがある。

---

## STEP 1：任せてよい仕事かを判定する（第2章）

五つの条件を確認する。三つ以上に「いいえ」がつくなら、委任は見送るか、範囲を絞る。

- [ ] **目的が言語化できる** — 何をもって完了とするか、文章で書ける
- [ ] **試行錯誤に意味がある** — 何度も試すほど良くなる性質の仕事である
- [ ] **検証が実行より安い** — できたものが正しいか、作るより楽に確かめられる
- [ ] **失敗が可逆である** — 間違えても元に戻せる
- [ ] **待ち時間で滞留していた** — 人間の都合で止まっていた工程である

### 特に注意すべき仕事（第9章）

次に当てはまるものは、検証コストが実行コストに近づく。委任の経済的意味が薄い。

- [ ] 網羅性が問われる（「見落としがないこと」が価値の中心）
- [ ] 判断の妥当性が問われる（「なぜ外したか」を確かめるには自分で調べるしかない）
- [ ] もっともらしさが高い（間違っていても読めてしまう成果物）

---

## STEP 2：委任の設計（第4章・第8章）

四項目を、文書で残す。テンプレートは付録Cを参照。

### 目標
- [ ] 手順ではなく、達成すべき状態を書いた
- [ ] **完了の定義**を書いた（何が揃っていれば終わりか）
- [ ] 何のためにやるのか（背景・用途）を書いた

### 前提
- [ ] 自分の頭の中にあって、相手にない情報を書き出した
- [ ] 社内固有の用語・定義を明示した
- [ ] 例外扱いしている対象を明示した

### 権限の範囲
- [ ] 使ってよい道具を列挙した
- [ ] **不可逆な操作**（送信・削除・決済・公開）を許すかを明示的に決めた
- [ ] 費用の上限を決めた
- [ ] アクセス範囲を、必要最小限に絞った

### 報告と停止
- [ ] 完了時の報告先を決めた
- [ ] 時間または費用の**上限**を設定した
- [ ] 「わからなくなったら止まって聞く」条件を書いた
- [ ] 行き詰まったときの扱いを決めた

---

## STEP 3：事故の予防（第10章）

### 委任の前に、必ず一度

- [ ] **「この目標を達成する、望ましくないやり方を三つ挙げよ」に答えた**

所要三分。これだけで防げる事故が多い。

### 六つの型への備え

- [ ] **静かな失敗** — 「できなかった」を報告する道を用意した
- [ ] **静かな失敗** — 代替手段を使ったら報告させる設定にした
- [ ] **字義どおりの達成** — 代理指標ではなく本来の目的を書いた
- [ ] **字義どおりの達成** — 副作用を見る指標を同時に設定した
- [ ] **もっともらしい誤り** — 出典の存在確認を、別工程に分けた
- [ ] **もっともらしい誤り** — 「確認できたこと」と「推測」を書き分けさせた
- [ ] **報告の最適化** — 悪い報告・リスクの記載を、形式として要求した
- [ ] **連鎖する自動化** — 他の自動処理との相互影響を図に描いた
- [ ] **連鎖する自動化** — フィードバックの輪に、遅延か上限を入れた
- [ ] **権限の拡大** — 権限を広げる際の承認手続きを決めた

---

## STEP 4：責任の設計（第11章）

**ここを飛ばすと、事故時に押しつけ合いになり、平時には誰も使わなくなる。**

- [ ] このエージェントの**オーナー**を、名前で決めた（一人。チームではない）
- [ ] オーナーは、**いつでも止める権限**を持っている
- [ ] オーナーは、**業務を理解している人**である（技術部門ではない）
- [ ] オーナーが異動・退職するときの引き継ぎ手順を決めた
- [ ] 責任の四つの位置（提供・設定・運用・結果）を関係者で合意した
- [ ] オーナーの責任の重さと、爆風半径の広さが釣り合っている

---

## STEP 5：検証の設計（第9章）

### 爆風半径を絞る

- [ ] 書き込み先を限定した（下書き領域のみ、など）
- [ ] 金額・件数の上限を設けた
- [ ] 外部への送信を制限した
- [ ] **まず小さく始める**範囲を決めた（全件ではなく十件、など）

### 段階的な信頼

いまの段階に丸をつける。

- [ ] 段階1：全件確認
- [ ] 段階2：抜き取り確認
- [ ] 段階3：例外のみ確認
- [ ] 段階4：事後確認のみ

- [ ] 次の段階へ進む条件を、**データで**定義した（印象ではなく）
- [ ] **一段階戻す条件**を、先に決めた

> 逆行の条件を先に決めておかないと、悪い兆候が出ても「たまたまだろう」と解釈してしまう。

### 記録

- [ ] 何を記録するかを決めた（全部ではなく、読む前提で）
- [ ] 記録を**実際に読む人と頻度**を決めた

> 「ログは取っています」は、読んでいなければ意味がない。

---

## STEP 6：運用開始後（第5章・第11章）

### 毎回

- [ ] 成果物の由来（データの時点・出典）を確認している

### 月次

- [ ] 抜き取り検査を実施し、誤り率を記録している
- [ ] 費用の実績を確認している

### 四半期

- [ ] 記憶の棚卸しをした（古い情報・間違った情報を消した）
- [ ] 権限の一覧を棚卸しした（いつの間にか広がっていないか）
- [ ] オーナーの在籍を確認した

### 年次

- [ ] STEP 0の一覧を作り直した
- [ ] まだ必要か（そもそも止めてよいのではないか）を検討した

---

## 文化の確認（第11章）

制度ではなく、上司の振る舞いで決まる部分。

- [ ] 「エージェントが変なことをした」と**言いやすい**環境がある
- [ ] 報告した人が、責められていない
- [ ] 前回の事故で、組織は**原因**を追及したか（人ではなく）

---

## 最後に一つだけ

すべてを一度にやろうとしなくてよい。

**最も効果が高い三つ**を選ぶなら、これになる。

1. **STEP 0** — いま何が動いているかを書き出す
2. **STEP 4** — オーナーの名前を決める
3. **STEP 5の爆風半径** — 不可逆な操作を人間の手元に戻す

この三つは、いずれも半日以内で終わり、事故の重大度を大きく下げる。
