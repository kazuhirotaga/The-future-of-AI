# 第4章 エージェントの解剖学

## なぜ仕組みを知る必要があるのか

「中身は知らなくていい。使えれば十分だ」

自動車の運転にエンジンの知識は要らない。この考え方は、多くの技術について正しい。

だが、エージェントには当てはまらない。理由は単純だ。

**あなたは、それを運転するのではなく、監督するからだ。**

部下を監督する管理職は、部下の脳の仕組みを知らない。だが、部下がどういうときに詰まり、どういうときに勘違いし、どういう報告の仕方をするかは知っている。知らなければ、任せ方を設計できない。

エージェントについて必要なのは、そのレベルの理解である。内部の数式ではない。**どう働き、どこで間違えるか**の理解だ。

この章では、それを四つの部品――ループ、道具、文脈、停止条件――に分けて見る。

---

## 部品1：ループ

エージェントの中心にあるのは、単純な輪だ。

```
   ┌──────────────────────────────┐
   │                              │
   ▼                              │
 観測 ──→ 計画 ──→ 行動 ──→ 評価 ─┘
（いま何が   （次に何を  （実際に  （うまく
  起きて      すべきか）   やる）    いったか）
  いるか）
```

これだけである。

観測し、計画し、行動し、評価する。評価の結果、目標に届いていなければ、また観測に戻る。届いていれば止まる。

驚くほど素朴だが、この輪が回る回数が、エージェントの働きの実質を決める。三回で終わる仕事もあれば、二百回回る仕事もある。

### 人間の仕事も同じ形をしている

この輪は、実は人間の仕事とまったく同じだ。

企画書を書くとき、あなたは資料を見て（観測）、構成を考え（計画）、書き（行動）、読み返す（評価）。読み返して違和感があれば、また資料に戻る。

違うのは速度と持久力だけである。人間は一日に何回もこの輪を回せない。集中力が切れる。エージェントは切れない。

### どこで壊れるか

輪が単純なぶん、壊れ方も決まっている。

**評価が甘いと、間違ったまま進む。**
「うまくいった」と自分で判定して次に進んでしまう。人間なら「なんとなく変だ」と感じるところを、感じない。この失敗は静かに起きて、後で発覚する。第10章の主題である。

**観測が古いと、存在しない現実に対処する。**
三十手前に見た状態を前提に、いまの行動を決めてしまう。その間に状況が変わっていれば、行動は的外れになる。人間で言えば「先週の情報で今日の判断をする」に当たる。

**計画が場当たりだと、同じ場所を回る。**
同じ手を、少しだけ変えて、何度も試す。人間なら三回で「これは筋が悪い」と気づくところを、二十回試す。時間と費用だけが溶ける。

これらは、**部下の失敗パターンとほぼ同じ**である。だから、部下を育てた経験のある人は、エージェントの設計に強い。

## 部品2：道具

ループの「行動」の部分が、道具の出番だ。

道具とは、エージェントが世界に手を伸ばす手段のことである。ファイルを読む、検索する、コードを走らせる、社内システムに問い合わせる、メールを送る。

### 道具の集合＝権限の設計

エージェントに何ができるかは、与えた道具で決まる。これは技術の問題ではなく、**権限設計の問題**である。

新入社員に、初日から本番データベースの削除権限を渡す組織はない。同じ判断が、エージェントにも必要になる。ところが実際には、「とりあえず全部使えるようにしておこう」という設定が、驚くほど頻繁に行われる。

原則を一つ挙げるなら、これだ。

> **渡した道具は、いつか使われる。**

「そんな使い方はしないだろう」は、根拠にならない。目的の達成に有効だと判断されれば、使われる。悪意ではなく、忠実さの結果として。

### 読む道具と、書く道具

道具を評価するとき、最も重要な区別は、能力の高さではない。

**取り返しがつくかどうか**である。

| 種類 | 例 | 失敗したときの代償 |
|---|---|---|
| 読む | 検索、ファイル読み取り、参照 | 低い（時間と費用のみ） |
| 書く（可逆） | 下書き保存、バージョン管理下の編集 | 中（戻せる） |
| 書く（不可逆） | メール送信、決済、外部への公開、削除 | 高い（戻せない） |

この三分類だけで、委任設計の八割が決まる。読む道具は気前よく渡してよい。不可逆な道具は、L3（承認つき実行）に留めるのが基本である。

第9章で扱う「爆風半径」という考え方は、ここから出発する。

## 部品3：文脈（コンテキスト）

エージェントには、作業机がある。

その机の上に載せられるものだけを見ながら、次の一手を決める。机の広さには限りがある。これがコンテキストウィンドウと呼ばれるものだ。

技術的な詳細は本書の範囲外だが、**実務的に効いてくる性質**が三つある。

### 性質1：机が広くても、端のものは見落とされる

机が広くなれば、たくさんの資料を載せられる。だが、載っているものすべてが等しく参照されるわけではない。人間が分厚い資料の真ん中を読み飛ばすように、機械にも似た偏りがある。

実務的な含意：**大量に渡せば伝わるとは限らない。** 重要なことは、量ではなく位置と明確さで伝える。

### 性質2：長く働くほど、机は散らかる

百手も作業を続ければ、机の上には試したこと、失敗したこと、途中の結果が山積みになる。人間なら整理するが、放っておくと机は散らかったままになる。

散らかった机の上では、判断の質が落ちる。長時間の作業ほど、後半の判断が怪しくなるのは、この理由が大きい。

実務的な含意：**長い作業は、区切って渡す。** 一晩で全部やらせるより、工程を分けて、それぞれ独立した机で作業させたほうが、結果が良いことが多い。これは人間のプロジェクト管理とまったく同じ知恵である。

### 性質3：机の上にないことは、存在しない

当たり前だが、重要だ。あなたの頭の中にある前提は、机の上に載せない限り、伝わらない。

「うちの会社では月初に締めるのが慣例だ」
「あの取引先は特別扱いしている」
「この数字は去年から定義が変わっている」

こうした暗黙の前提が抜けたまま作業すれば、もっともらしく間違ったものが出てくる。しかも夜通し出てくる。

実務的な含意：**委任の質は、前提の言語化の質に等しい。** これは第8章で扱う「委任のスキル」の核心である。

## 部品4：停止条件

最後の部品が、最も軽視されている。

**いつ止まるか。**

エージェントは、目標に到達したら止まる。だが、「到達した」を判定するのはエージェント自身だ。判定基準が曖昧なら、二つのことが起きる。

**早く止まりすぎる。**
八割の出来で「完了しました」と報告する。人間なら「まだ荒いですが」と前置きするところを、しない。

**止まらない。**
完璧を目指して延々と改善を続ける。夜通し。費用を使いながら。

止め方の設計には、四種類ある。

| 停止条件 | 内容 | 使いどころ |
|---|---|---|
| 達成 | 目標が満たされた | 完了の定義が明確な仕事 |
| 上限 | 試行回数・時間・費用の上限に達した | 探索的な仕事の安全弁 |
| 行き詰まり | 進展がない状態が続いた | 筋の悪い方向への深追いを防ぐ |
| 要確認 | 人間の判断が必要な地点に来た | 不可逆な行動の直前 |

四つ目が特に重要だ。**「わからなくなったら止まって聞く」を設計しておく**こと。これがないと、エージェントは推測で進む。推測で進んだ結果は、朝になってから発覚する。

実務では、上限（時間・費用）と要確認の二つを必ず設定することを勧める。達成だけを条件にすると、暴走ではなく**静かな浪費**が起きる。

## 四つの部品を、一枚にまとめる

```
     ┌─────────────────────────────────────┐
     │           目標（ゴール）              │
     └──────────────┬──────────────────────┘
                    │
        ┌───────────▼──────────────┐
        │   ┌──── ループ ────┐      │
        │   │ 観測→計画→行動→評価 │◄─── 文脈（机）
        │   └───┬────────┬────┘      │      ・前提
        │       │        │            │      ・履歴
        └───────┼────────┼────────────┘      ・資料
                │        │
                ▼        ▼
            停止条件    道具
            ・達成      ・読む（安全）
            ・上限      ・書く／可逆
            ・行き詰まり ・書く／不可逆（要注意）
            ・要確認
```

委任を設計するとは、この図の各要素を埋めることに他ならない。

- 目標は何か（何をもって完了とするか）
- どんな道具を渡すか（特に、不可逆な道具を渡すか）
- どんな前提を机に載せるか
- どこで止まるか

四つとも埋まっていないまま委任すると、埋まっていない部分がエージェント側の推測で埋められる。推測は、あなたの視界の外で行われる。

## 反対側から見る：仕組みを知りすぎることの罠

ここまで書いておいて逆のことを言うが、**仕組みの理解が細かすぎるのも問題**である。

技術に詳しい人ほど、内部の挙動を追いかけすぎて、肝心のことを見落とす傾向がある。肝心のこととは、**その仕事を任せてよいのか、誰が責任を持つのか**という問いだ。

エンジンの仕組みに詳しくても、その車をどこへ走らせるべきかは決まらない。

本書がこの章で提供したかったのは、監督に必要な最小限の解像度である。これ以上の理解は、必要になったときに得ればよい。

---

## この章の要点

- エージェントの中心は「観測→計画→行動→評価」の単純なループ。人間の仕事と同じ形をしている。
- 壊れ方も人間と似ている。**評価が甘い／観測が古い／同じ場所を回る**。
- 道具の集合＝権限設計。最重要の区別は能力の高さではなく、**取り返しがつくか**。
- 文脈には三つの性質。**端は見落とされる／長く働くと散らかる／載せていない前提は存在しない**。
- 停止条件は四種類（達成・上限・行き詰まり・要確認）。**上限と要確認は必ず設定する。**
- 委任の設計とは、目標・道具・文脈・停止条件の四つを埋めること。埋めなければ、推測で埋められる。

## あなたの職場で考えること

1. あなたが最近、人に任せた仕事について。目標・道具・前提・停止条件の四つを、明示的に伝えていたか。伝えていなかったのはどれか。
2. あなたの職場で、エージェントに「不可逆な道具」を渡している例はあるか。それは意図した設計か。
3. 「わからなくなったら聞いてくれ」を、あなたは相手に伝えているか。伝えなければ、相手は推測で進む。人でも機械でも同じである。
